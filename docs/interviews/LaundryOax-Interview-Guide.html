Two routes through the material

Five rules for accurate answers

  2. Explain what an ACK means and where a transaction stops.
  3. Give measured numbers only with their test conditions. Eight simulated machines is not a production fleet size.
  4. Separate personal experience from AI-assisted implementation and hypothetical incident responses.
  5. When you do not know, identify the missing assumption and the experiment or authoritative documentation that would resolve it.

LaundryOax architecture and code map

The source baseline is 545e6a3. The working local path and the proposed AWS transport share an inbox processor but have different acknowledgment semantics.

Working local path

Edge capture -> SQLite outbox -> HTTP API -> durable inbox -> ordered worker -> machine state and notifications -> Angular polling

AWS design: future MQTT publisher -> IoT Core rule -> standard SQS -> SQS receiver -> same durable inbox

The edge executable is a separate process. API, inbox worker, and optional SQS receiver are hosted together. In local demo mode, FleetDb is SQLite and authentication uses a fixed loopback-only tenant/operator identity. A separate SQL Server connection remains available for the original disabled legacy API.

AWS transport design

MQTT publish -> IoT identity policy -> topic-derived tenant and device -> encrypted SQS -> inbox commit -> SQS delete
Repeated receive failures -> DLQ

This path is source/configuration, not a deployed validation result. The repository does not contain the MQTT edge publisher or a downstream application-ACK topic. A broker PUBACK must not be substituted for the HTTP inbox receipt. The native IoT SQS action requires a standard queue; application ordering is deliberate. AWS IoT SQS action.

The three commit boundaries

BoundaryAtomic workResponsibility after commitFailure after commit
Edge captureSequence increment plus outbox insertEdge must retain and deliver event until application ACKReopen file and replay the same identity

No transaction includes HTTP delivery or the SQS DeleteMessage operation. Idempotency closes those retry windows for retained identities; it does not create a cross-system disaster recovery guarantee.

Invariants and assumptions

  • Identity: TenantId plus EventId identifies an immutable typed payload; a hash detects conflicting reuse.
  • Sequence ownership: TenantId plus DeviceId plus Sequence is unique. A new stream begins at one.
  • Application order: only LastSequence + 1 is eligible. No global order is claimed across machines.
  • Atomic projection: machine state, processed marker, and a qualifying notification are committed together.
  • Tenant access: queries use signed/authenticated tenant identity. There is no database RLS policy or global query filter.
  • Limits: no device epoch, CycleId, explicit schemaVersion, deduplication retention job, or gap recovery endpoint.
  • Durability assumptions: healthy persisted storage, correct filesystem/database behavior, and retention of the authoritative data. A historical database restore can violate the retained-event assumption.

Sizing practice with explicitly hypothetical inputs

Offline buffer: event rate × outage duration × stored bytes per event, plus indexes, WAL, metadata, and headroom. One 1 KiB event every ten seconds for twenty-four hours gives 8,640 events and 8,847,360 raw bytes, approximately 8.44 MiB per device. This excludes actual database overhead and is not a supported capacity claim.

Ingestion rate: N/t. Ten thousand hypothetical devices at a ten-second interval would create 1,000 events per second before duplicates/reconnect bursts. No such load test has been performed.

Drain time: B/(mu-lambda), only if service rate mu exceeds arrival rate lambda and events are eligible. A hypothetical 60,000-event backlog with mu=500/s and lambda=100/s drains in 150 seconds under ideal conditions. Sequence gaps, database locks, and CPU/network limits can invalidate this estimate.

Write amplification: each normal event creates the inbox and accepted audit, then updates machine and inbox and inserts processed audit; phase transitions may insert a notification. Edge counter/outbox/ACK writes and indexes/logs add more work. Measure bytes and IOPS rather than assuming one disk write per event.

Architecture and distributed systems

Q016 Walk through the complete working path.

Evidence status: Implemented.

Capture allocates a device sequence and writes its event in one SQLite transaction. Replay sends the stored JSON to /api/telemetry. Device authentication binds the caller to a tenant and device. Accept saves an inbox event and audit entry before returning a receipt. Process applies the next sequence and commits machine state, audit, and any completion or fault notification together. The dashboard polls the resulting projection.

Code or follow-up: edge/Outbox.cs · edge/Program.cs · IoT/EventPipeline.cs · client/src/main.ts

Q017 Where are the durability boundaries?

Evidence status: Implemented.

There are three distinct commits: the edge outbox transaction, the API inbox SaveChanges call, and each worker processing transaction. A successful receipt means the inbox committed; it does not mean the machine projection or notification is already updated. The SQS adapter uses that same inbox commit as its delete boundary.

Code or follow-up: edge/Outbox.cs · IoT/EventPipeline.cs · IoT/SqsWorker.cs

Q018 Do you provide exactly-once processing?

Evidence status: Implemented with limits.

I would say at-least-once delivery attempts with idempotent database effects within the implemented identity and transaction boundaries. The database prevents a retained event from applying twice, but that is not a universal exactly-once delivery guarantee. Restoring old state, removing deduplication records, or adding an external notification provider creates new reconciliation boundaries.

Q019 Why not process everything synchronously in the request?

Evidence status: Implemented.

Persisting first keeps acknowledgment separate from projection work, and a worker can retry after the request finishes. However, Accept and Process share a process-wide semaphore, so requests can still wait behind a processing batch. The current design improves responsibility separation without proving independent resource isolation or low latency under load.

Q020 What is eventually consistent here?

Evidence status: Implemented.

The API can acknowledge an event before the worker updates the machine. The browser refreshes later, so receipt, projection, and display have different observation times. The snapshot endpoint also makes several separate queries without a shared read transaction; under concurrent writes, its counters and lists can briefly reflect slightly different database states.

Q021 How are events ordered?

Evidence status: Implemented.

The worker joins pending events to their machine and only selects an event whose sequence equals LastSequence + 1. Ordering is per tenant and device, not global. ReceivedUtc chooses among eligible events; it is not the correctness mechanism. A gap on one machine does not logically block another machine's eligible sequence.

Code or follow-up: IoT/EventPipeline.cs

Q022 Why use sequence numbers instead of timestamps?

Evidence status: Implemented.

Capture order is explicit in a persisted integer counter. Device clocks can drift or be corrected, and delayed events can arrive out of order, so timestamps are unsuitable as the only ordering key. ObservedAt remains useful for freshness and analysis, but it is not used to decide the next event to apply.

Code or follow-up: edge/Outbox.cs · IoT/EventPipeline.cs

Q023 How are duplicates detected?

Evidence status: Implemented and tested.

The inbox primary key is TenantId plus EventId. Accept hashes the serialized typed event and compares that hash when the key already exists. Matching content gets a duplicate receipt; conflicting content produces a conflict. A separate unique index on tenant, device, and sequence prevents two distinct events from owning the same sequence.

Code or follow-up: IoT/EventPipeline.cs · IoT/FleetDb.cs

Q024 Does the hash authenticate an event?

Evidence status: Implemented.

No. SHA-256 here detects content reuse under an existing event identity; it is not a signature or an HMAC. Device authentication and TLS provide separate trust boundaries. The hash is over reserialized typed data, not the original wire bytes, so it should not be described as byte-for-byte verification of the transport payload.

Code or follow-up: IoT/EventPipeline.cs · IoT/Security.cs

Evidence status: Implemented and tested.

Accept can persist sequence two, but Process finds no eligible event for that device until sequence one arrives. After one is accepted, a worker pass applies both in sequence. A test asserts that no processing occurs before the gap is filled and that completion creates one notification afterward.

Edge processing and recovery

Q031 Why choose SQLite at the edge?

Evidence status: Implemented.

It offers embedded transactional persistence without requiring a local database server. This edge uses WAL and synchronous FULL, and capture commits the counter and event atomically. That reduces crash-related inconsistency when the filesystem honors durability requests. It does not protect against destroyed disks, exhausted capacity, malicious writes, or an incorrect sensor driver.

Code or follow-up: edge/Outbox.cs

Q032 What is actually buffered?

Evidence status: Implemented.

Immutable serialized telemetry including EventId, tenant, device, sequence, observation time, phase, progress, temperature, moisture, and turbidity. The outbox also stores attempts and the next eligible retry timestamp. Separate persistent sequence rows survive acknowledgment deletes so the counter does not restart when the outbox becomes empty.

Code or follow-up: edge/Outbox.cs · IoT/Models.cs

Q033 How are sequence numbers allocated safely?

Evidence status: Implemented and tested.

Capture starts a transaction, inserts or increments the sequence row using an upsert with RETURNING, validates the resulting event, then inserts its payload before committing. Failure rolls back both operations. A test proves invalid capture does not consume sequence one. The counter is scoped by tenant and device.

Code or follow-up: edge/Outbox.cs · tests/ReliabilityTests.cs

Read-only SQL for sequence gaps

Use an authorized operational connection. This query is intentionally tenant/device scoped in its grouping but views all returned tenants; it is for an administrator, not a tenant-facing API.

SELECT m.TenantId, m.DeviceId, m.LastSequence,
       MIN(e.Sequence) AS FirstPendingSequence,
       COUNT(e.EventId) AS PendingCount,
       MIN(e.ReceivedUtc) AS OldestPendingReceivedUtc
FROM Machines AS m
JOIN Events AS e
  ON e.TenantId = m.TenantId AND e.DeviceId = m.DeviceId
WHERE e.ProcessedUtc IS NULL
GROUP BY m.TenantId, m.DeviceId, m.LastSequence;

If FirstPendingSequence exceeds LastSequence + 1, investigate the missing sequence. If it equals the next sequence, inspect worker exceptions, database locks, and process activity. Do not assume every pending row is caused by a gap. SQL Server and SQLite timestamps/tools differ; verify the schema and execution plan in the environment you are inspecting.

-- Edge database, separate from FleetDb.
SELECT tenant, device, MIN(sequence) AS oldest_sequence,
       COUNT(*) AS pending_count, MAX(attempts) AS max_attempts
FROM outbox
GROUP BY tenant, device;

SELECT id, tenant, device, sequence, attempts, next_attempt
FROM outbox
ORDER BY tenant, device, sequence
LIMIT 25;

The second query uses SQLite LIMIT and is for the edge store. next_attempt is Unix milliseconds. A future timestamp can mean normal backoff; it is not necessarily a stuck process.

Sequence gap recovery procedure

  1. Identify tenant, device, LastSequence, earliest pending sequence, and last successful processing time.
  2. Search the inbox and edge store for the missing identity; inspect receiver/DLQ errors if the AWS path is in use.
  3. If the original event still exists, replay it unchanged through the normal ingestion path after fixing the transport/provisioning issue.
  4. Verify application order and that later pending events drain. Confirm notifications were not duplicated.
  5. If the event is irrecoverable, document the loss. The current application has no supported resynchronization endpoint. Design an explicit audited epoch/snapshot recovery before bypassing ordering; do not silently increment LastSequence.

Backup restore and reconciliation

Current status: a proposed operating procedure, not implemented automation or a completed recovery drill.

  • Define the authoritative store for each acknowledged event and the required replay horizon before setting RPO/RTO.
  • Use database-supported backups/PITR and protected storage. For SQLite, use its online backup interface or stop writers safely; copying only a live .db can omit WAL content.
  • Test restore into an isolated database with the exact application/schema version. Verify integrity, machine sequence checkpoints, event identities, and notifications.
  • Reconcile acknowledged events after the restored timestamp. Edge ACK deletes and SQS deletes mean neither transport is necessarily still a recovery source.
  • Keep a record of actual recoverable point, measured recovery time, and unresolved gaps. Do not declare zero loss without evidence.
  • Restore access/configuration safely, resume producers in a controlled order, monitor duplicates/conflicts/lag, and preserve an incident audit trail.
